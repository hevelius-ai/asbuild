## JS-1 Vitest JUnit (run 43649713076, vitest 5.1.0): PROVEN, with one design consequence

- `classname` = the test file's path (`tests/acceptance/S1/assert.test.ts`); `name` = the describe chain joined by ` > ` plus the test title (`S1-C8 the list > S1-C9 counts a`). Check IDs in titles are readable; the story folder is in the path.
- `<failure type=...>` is filled: `AssertionError` for `expect(...)` failures, `TypeError`, `Error`.
- A file that cannot load (missing module: `Cannot find module ... ERR_MODULE_NOT_FOUND`; syntax error: `Transform failed`) becomes ONE testcase whose `name` equals its `classname` (the path), type `Error`. **The file's own tests do not appear at all**, so the checks in it must be known from the story and lock, not from the results.
- A missing export (named ESM import or namespace member) is `TypeError: notThere is not a function`, the same type and shape as a real app bug (`Cannot read properties of undefined`). Not distinguishable by type alone.
- Skipped: `<skipped/>`. Parametrised `test.each` gives one testcase per row with the row in the title.
- Exit code 1 when anything fails; the one-file run (as a fails-before overlay would run it) also writes its file.

## JS-2 Jest + jest-junit, default options (run 43649718653, jest 30.5.2, jest-junit 17.0.0): DISPROVEN as usable by default

- `classname` = `name` = the test title; **no file path anywhere**; testsuite `name="undefined"` for top-level tests.
- **Files that fail to load (missing module, syntax error) are absent**: 9 tests reported, the two broken files missing entirely.
- Assertion failures carry no type: the body starts `Error: expect(received).toBe(expected)`.
- Consequence: default jest-junit cannot be used. JS-2b tests the reporter's options and Jest's own `--json` file.

## JS-2b Jest options and Jest's JSON (run 43649857624, jest 30.5.2): PROVEN, Jest's own `--json` is the better source

- jest-junit with `JEST_JUNIT_CLASSNAME={filepath}`, `JEST_JUNIT_ADD_FILE_ATTRIBUTE=true`, `JEST_JUNIT_REPORT_TEST_SUITE_ERRORS=true`: file path present; a file that fails to load appears as `<error>` under classname "Test suite failed to run" with the path as name. With `JEST_JUNIT_TITLE={title}` the describe titles are lost (`shows 2 items` without `S1-C8 the list`): the title template must include the describe chain. Assertion failures still untyped (`Error: expect(received)...`). It also adds a dependency (jest-junit) to the user's project.
- `jest --ci --json --outputFile=...` (built in, no extra package): per file `name` (absolute path), `status`, `message` (for a file that failed to run: "Test suite failed to run ... Cannot find module" / "unexpected token"); per test `ancestorTitles` (describe chain), `title`, `status` (passed, failed, pending), `failureMessages`, and `failureDetails[].matcherResult.name` (`toBe`) **only when an `expect` matcher failed**: a clean "failed by assertion" signal. TypeError and plain Error carry no matcherResult.
- Exit code 1 when anything fails.

## JS-3 Project Vitest config against AsBuild's own (run 43649795474, vitest 5.1.0): PROVEN, the threat is real and the obvious guard breaks real projects

- With the project's own `vitest.config.ts` whose `setupFiles` makes every `toBe` pass: the wrong `count` PASSES both checks, exit 0. **A changed runner config or setup file can turn a failing check green.**
- With AsBuild's own config (an import-free object loaded from outside the project, `--config <path>`, with or without `--root`): the cheat is gone and the relative-import check fails by assertion, correctly; but the check importing `@/count` fails with `Cannot find package '@/count'`: **the project's path alias (`@/`, standard in Vite and Next.js apps) is lost**, so that check could never be judged.
- `--config=false`: startup error. `--setupFiles=` on the command line: unknown option. Neither is a way out.
- Consequence for the design: either protect the runner config and every file it loads (change = WAITING FOR YOU), or build AsBuild's config from the project's config minus setup files and plugins (to prove; an alias can itself point `vitest` at a fake, so aliases need a rule too).

## JS-4 Vitest's JSON reporter (run 43650050646, vitest 5.1.0): PROVEN, the same shape as Jest's

- Top keys as Jest's (`testResults`, `numFailedTests`, ...); per file `name`, `status`, `message` (a file that cannot load: `Cannot find module ...`, `Transform failed ...`, with no test entries); per test `ancestorTitles`, `title`, `status` (`passed`, `failed`, `skipped`; Jest says `pending`), `failureMessages`.
- No `failureDetails`: an assertion failure is told by the message prefix `AssertionError:`. A missing export reads `TypeError: __vite_ssr_import_1__.notThere is not a function` (the import shows in the message).
- Consequence: one reader can take both Jest's and Vitest's JSON; only the "failed by assertion" rule differs (Jest: `failureDetails[].matcherResult`; Vitest: `AssertionError:` prefix).

## JS-5 AsBuild's Vitest config built from the project's (run 43650053306, vitest 5.1.0, node 24.22.2): PROVEN

- AsBuild's config (an import-free `.mjs` outside the project, a function that imports the project's `vitest.config.ts` at run time, which Node 24 loads as TypeScript) kept only the project's aliases whose key is not `vitest`/`@vitest`/`vite` and whose target lies inside the project: log `alias dropped: vitest`, `aliases kept: ["@"]`.
- With it, the project's cheating setup file and its transform plugin were not loaded: the wrong `count` failed by assertion (`AssertionError: expected 'words: 2' to be 'words: 3'`), the correct check passed. The `@/` import worked.
- Limit (as D16 for Python): the project's config file is still executed (in the untrusted job, which runs the pull request's code anyway), and app code or install scripts can still change the test tool on disk. This guard stops a changed config or setup file, not a determined forger; the trusted half's checks (locks, protected files, fails-before) stay the safety net.
