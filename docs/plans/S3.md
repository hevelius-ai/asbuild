# S3 plan: the install page

Story S3 of AsBuild Core (HANDOVER section 4). Estimate 1 to 2 agent hours; at 2 hours without the criteria passing, the story stops for the owner's choice (D20). Written 10 Nov 2026, before any code.

## Criteria (HANDOVER section 4)

1. Given the install page, when Claude Code follows it word for word on `hevelius-ai/auto-job-search`, then the plugin is installed, the two workflow files are on main, and the next pull request gets a verdict.
2. One optional settings line: Claude Code's own deny rule on the acceptance-test folder, and what it does not cover (a script that opens a file itself is not blocked; CI is the check). No `asbuild` command, no uv, no Stop hook line.
3. Getting the verdict (D19): the page tells the reader's agent to run the plugin's wait script after each push; `gh pr checks --watch` is not enough.

## What S3 delivers

1. **The install page:** the `## Install` section of `README.md`. In order:
   - **What your repository needs:** a GitHub repository with GitHub Actions switched on; Git (the marketplace is cloned with Git, G6 run 2); Python code whose tests run on Python 3.12 with pytest, and a `requirements.txt` at the root that lists pytest (the check installs from it); pull requests from branches of the same repository (the verdict job skips forks). The names AsBuild expects: `dev-docs/stories/`, `tests/acceptance/`, `locks.json`, build branches `build/S<n>`.
   - **Install the plugin:** in Claude Code, `/plugin marketplace add hevelius-ai/asbuild`, then `/plugin install asbuild@hevelius-ai`. From a script, CI or Claude's own shell: `claude plugin marketplace add hevelius-ai/asbuild` before `claude plugin install asbuild@hevelius-ai` (G6 runs 2 and 3: the install fails when the marketplace was never added).
   - **Add the two workflow files in a pull request:** download `workflows/asbuild-test.yml` and `workflows/asbuild-verdict.yml` from `hevelius-ai/asbuild` into `.github/workflows/`, open a pull request and merge it. This pull request gets no verdict, because the workflows are not on main yet. The login that pushes workflow files needs GitHub's `workflow` scope.
   - **Your first story:** `/asbuild:story`. Its pull request always gets WAITING FOR YOU; merging it approves the checks.
   - **Getting the verdict:** after each push, `/asbuild:verdict`.
   - **The deny line each story adds** (decision S3-1, below, now D26) and what it does not cover.
   - No time claim (G6 timed uv and a plugin install only, not the workflow files).
2. **The verdict skill** `plugin/skills/verdict/SKILL.md`, run as `/asbuild:verdict` (small addition, reported here and in the PR). It runs `python "${CLAUDE_PLUGIN_ROOT}/scripts/asbuild_wait.py"` after a push and says what to do for each exit code. Why a skill: D19 needs the agent to reach the plugin's wait script, and the Claude Code docs say `${CLAUDE_PLUGIN_ROOT}` is substituted in a skill's text but is not in the Bash tool's environment. A plugin `bin/` folder would put it on the Bash tool's PATH, but claude.ai and Cowork don't install a plugin that has one, which would block the D17 directory listing (plugins reference, read 10 Nov 2026). The skill says to run the script in the background: it waits up to 20 minutes by default, and Claude Code's Bash tool stops a foreground command after at most 10.
3. **The plugin version goes to 0.2.0.** A set `version` keeps users on that version until it changes (plugins reference), so a new skill needs a new version.
4. **One line in the story skill** pointing the build at `/asbuild:verdict`.
5. **The S2 records** (`records/after-S2`, two commits) ride in this PR, as agreed.

## Decision S3-1 (the owner's): where the deny rule goes

Proved on 10 Nov 2026 with two headless Claude Code 2.1.319 runs on Windows (`claude-haiku-5-5`, $0.27): the rule `Edit(/tests/acceptance/**)` denies the Write tool creating a **new** file in `tests/acceptance/S9/`, both from `.claude/settings.json` and from `--disallowedTools`; a write to `app/` passes. So a deny rule in the project's settings also stops `/asbuild:story` writing a new story's tests.

- **A. The settings line, as written in the handover:** `"permissions": {"deny": ["Edit(/tests/acceptance/**)"]}` in `.claude/settings.json`. Every session is covered. Cost: `/asbuild:story` cannot write its tests while the line is there, so the page must say to remove it for each story and put it back after. Easy to forget either way.
- **B. The same rule as a start flag for build sessions:** `claude --disallowedTools "Edit(/tests/acceptance/**)"`. Story sessions start without it. Same protection where the build happens; nothing to remove. Cost: not "under `permissions.deny`" in a settings file as the handover says; it must be typed (or saved as a shell alias) for each build session, and a session started without it has no protection (CI still checks).
- **C. One settings line per merged story:** `Edit(/tests/acceptance/S1/**)`, a new entry added after each story merges. Protects exactly the locked tests and never blocks a new story. Cost: the list grows by one line per story, and someone must add each line; having the story skill add it is new scope.

All three say what is not covered: a script that opens a file itself is not blocked; CI is the check.

**The owner's answer (10 Nov 2026, D26): C, with the lines added automatically, on by default, never pruned.** The story-time checks' `--lock` adds `Edit(/tests/acceptance/S<n>/**)` to `.claude/settings.json` (creating it if needed, keeping every other setting, never twice), after every check passes and only when the lock is written. The settings file is read before anything is written, so a file that is not valid JSON, or whose `permissions` or `permissions.deny` has the wrong shape, stops the run with exit 2 and changes nothing. The story skill commits the file with the story, so the owner's merge approves the checks and switches on their protection together. Lines are never pruned: a story's tests stay locked for every later build. Size: about 0.5 to 1 agent hour, inside S3's estimate.

Proved on 10 Nov 2026 with one more headless run ($0.25): a deny line written to `.claude/settings.json` during a `claude -p` session did not apply to that session (a later write to the folder passed), so the story session can still fix its own tests after locking; the line applies from the next session. Whether an interactive session picks up the change is not proved, so the skill says: to change a check later, remove the story's line, start a new session, change the test there, then run the checks again (review round 1: by the same evidence, removing the line does not lift it in a session that started with it).

## Premortem: how S3 could fail

1. **The page is right on paper and wrong live** (a command, file name or install id drifts). Test: S3-C1 checks the install id, the marketplace order and the download URLs against the repository's files (the git, gh and curl lines are left to the live run); the live run on auto-job-search is the final check, and any fix is one more asbuild PR.
2. **Installed plugins never see the new skill** because the version did not change. Mitigation: version 0.2.0; the live run installs fresh and lists the skills.
3. **The deny rule blocks the story skill, or the line damages the reader's settings.** Proved and decided (D26): one line per story, added last. Tests: other settings kept, no duplicate, nothing written on a failed check or a refused lock, an unreadable settings file stops the run before anything is written.
4. **The agent forgets to fetch the verdict after a push.** The skill's description names the trigger, but loading it is the model's choice. Stated limit; the page also tells the person to ask for `/asbuild:verdict`. The live run records whether it was used.
5. **The reader's repository does not meet the needs** (no `requirements.txt`, tests that need another Python) and every verdict is UNRESOLVED. The page names each need; the verdict skill says what UNRESOLVED asks for.

The PR counts how many review findings fall in these five areas.
