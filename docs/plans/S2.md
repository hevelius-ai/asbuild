# S2 plan: the skill and its story-time checks

Story S2 of AsBuild Core (HANDOVER section 4). Estimate 4 to 8 agent hours; at 8 hours without the criteria passing, the story stops for the owner's choice (D20). Written 10 Nov 2026, before any code.

## Criteria (HANDOVER section 4)

1. Given a story with two checks, when the skill runs, then the story file holds the owner's words byte for byte, there are two tests (one per check), both story-time checks pass, and a story pull request is open.
2. Given a test that passes on main, or fails for a reason other than an assertion, or asserts values other than the approved examples, when the story-time checks run, then they fail and say why.
3. The skill stays under 100 lines.

1. **The plugin** in `plugin/`, Claude Code's standard layout (checked against code.claude.com/docs/en/plugins-reference on 10 Nov 2026):
   - `plugin/.claude-plugin/plugin.json`: name `asbuild`, version `0.1.0`, the D14 description, author Hevelius AI Group LLC, MIT.

3. **The skill finds its scripts** through `${CLAUDE_PLUGIN_ROOT}`, which Claude Code substitutes in a skill's text (the docs say it isn't in the Bash tool's environment, so the skill writes it in its text, never as `$CLAUDE_PLUGIN_ROOT` in a command).

## How the skill works (G5's conversation, G4's story format)

1. **The owner's words first.** The skill copies the request into the story's "Request" section exactly as written: no fixes to spelling, punctuation or line breaks.
2. **The conversation** follows G5's rules: one plain question at a time, at most three or four, then a checklist of 2 to 5 sentences, each with one to three exact examples, approved line by line.
3. **The story file** `dev-docs/stories/S<n>/story.md`: title, Request, Criteria table, and the Plain checklist with a third column, `Examples (approved)`, holding each exact value in backticks (`` `words: 3` ``). The engine's story parser reads only the first two columns, so S1's stories and receipts are unchanged.
4. **One test per check** in `tests/acceptance/S<n>/`, named `test_S<n>_C<m>_<words>`. It drives the app the way a person does where it can, asserts each approved example literally, and uses only the standard library and pytest. No conftest: CI runs these with `--noconftest`.
5. **Branch `story/S<n>`** from a freshly fetched `origin/main`. It runs `python ${CLAUDE_PLUGIN_ROOT}/scripts/asbuild_story_check.py S<n> --lock` with the Python that runs the project's tests (C5). If a check fails, the skill fixes the test, never the owner's words or examples. After three failed attempts it stops and tells the owner (playbook 2.2).
6. **The story pull request:** commit, push, `gh pr create`. The body lists the checklist and says that merging it is the approval. The skill builds nothing in the same pull request.

## The story-time checks (`asbuild_story_check.py`)

Standard library only, run with the project's own Python and pytest. Exit 0 when every check passes, 1 when one fails (one line per problem, saying why), 2 when it cannot run (no story file, not a git repository, no base branch, pytest missing).

- **The story file is complete:** a non-empty Request; 1 to 5 checks, each `S<n>-C<m>` with a plain sentence and 1 to 3 examples.
- **One test per check:** exactly one test function in `tests/acceptance/S<n>/` carries each check ID (the engine's whole-word rule), and every test there carries one of the story's IDs.
- **Check 1, fails on main by assertion.** This mirrors CI's fails-before run (`c3_overlay.py`). It makes a git worktree of the base (`origin/main` by default), copies the story's acceptance folder from the working tree into it, and runs pytest with CI's hardened flags (`--noconftest`, `-p no:cacheprovider`, plugin autoload off, JUnit XML). Per test:
  - passes → "passes already on main: it checks nothing new";
  - setup or collection error → "could not run on main: …";
  - failure whose message does not start with `assert`, `AssertionError` or `Failed:` → "fails on main for a reason other than an assertion: …".

  These three message forms were checked on pytest 9.2 (10 Nov 2026): `assert …`, `AssertionError: …`, and `Failed: DID NOT RAISE` from `pytest.raises`. TypeError, NameError, ModuleNotFoundError and fixture errors carry their own names. This is stricter than CI's rule, which also counts a TypeError as a real failure, so a test that passes here also passes CI's fails-before check.
- **Check 2, asserts the approved examples:** F4's `example_check.py`, Python part only (TypeScript is parked), ported unchanged except for the matching rule. An example string matches an asserted string that equals it or, at 4 characters or more, contains it as a whole value: no letter or digit right beside it, and no decimal or thousands part beside an edge digit (so `words: 3` is not inside `words: 30`, `words: 3.5` or `words: 3,000`); or an asserted number whose text equals it (review rounds 1 and 2). A missing example → "does not check the approved example `…`".
- **`--lock`**, only when everything passes: adds a lock entry for each `.py` file in `tests/acceptance/S<n>/` to `locks.json`. It keeps every other story's entries. It refuses to change an entry locked on the base, which the owner's merge approved. It replaces this branch's own earlier entries for the story, so a story revised before approval can be locked again, and a renamed or removed file leaves no entry behind (review rounds 1 and 2). The hash function is a copy of `engine/lock_check.entry`, because the plugin ships alone, and a test holds the two equal.

## Acceptance tests (written first, seen failing, then locked by the owner's merge)

In `tests/acceptance/S2/`. Each builds a small git repository in a temporary folder: a tiny app on `main`, then a story with its tests in the working tree. It runs the script as a separate process, as the skill does.

| Check | Criterion | Test |
| --- | --- | --- |
| S2-C1 | A two-check story: both story-time checks pass, two tests, lock entries written and equal to the engine's | `test_S2_C1_two_check_story_passes_and_locks` |
| S2-C2 | A test that passes on main: the checks fail and say so | `test_S2_C2_test_passing_on_main_fails_with_reason` |
| S2-C2 | A test that fails for another reason (missing import, TypeError): the checks fail and say so | `test_S2_C2_non_assertion_failure_fails_with_reason` |
| S2-C2 | A test that asserts other values than the approved examples: the checks fail and name the example | `test_S2_C2_unapproved_values_fail_with_reason` |
| S2-C3 | The skill is under 100 lines, with valid frontmatter, and names the script through `${CLAUDE_PLUGIN_ROOT}` | `test_S2_C3_skill_under_100_lines` |

**What CI cannot show:** the skill is instructions for a model, so no CI test can run it. Criterion 1's model-driven half (the owner's words saved byte for byte, two tests written, a story pull request opened) is shown live. A headless Claude Code session on `claude-sonnet-5-5`, loading the plugin with `--plugin-dir`, runs `/asbuild:story` in a clone of `hevelius-ai/asbuild-demo` with a fixed two-check request. That session runs on its own branch and opens a real story pull request on the demo. A script then compares the story file's Request section with the request bytes. The run is recorded in the PR (model, cost, PR link, byte comparison). Because a headless run cannot answer questions, its prompt says the checklist is approved as proposed for this test run; the owner's real approval is still the merge.

Also checked locally and recorded: `claude plugin validate . --strict` and `claude plugin validate ./plugin --strict`.

## Premortem: how S2 could fail

1. **The story-time check and CI disagree:** the script passes a test that CI's fails-before check later calls existence-only or already passing, so the build waits. Mitigation: the same worktree overlay and flags as `c3_overlay.py`, and a stricter rule. Test: the S2-C1 fixture feeds the script's JUnit file to `engine.junit_classify` and asserts every test is `strong`.
2. **The plugin's lock hash drifts from the engine's**, so every later build PR shows LOCK_CHANGED. Test: plugin and engine entries are equal on CRLF, BOM, trailing-space and plain files, and on the S2-C1 fixture.
3. **The example matcher flags an honest test**, as in F4's one false flag from a loop variable, and blocks a story. Stated limit, with a test row. The script's message says to assert the approved value literally; the skill says the same.
4. **The model paraphrases the owner's words** or drifts from the format, or the skill grows past 100 lines. The S2-C3 test counts lines. The skill puts the byte-for-byte rule first. The live run compares bytes.
5. **The script runs with the wrong Python** (no pytest), or on Windows paths or worktrees it was not tried on. Exit 2 with "pytest is not installed for this Python: run this with the Python that runs your tests", with a test. The live run and the local acceptance runs are on Windows; CI runs on Linux.

The PR counts how many review findings fall in these five areas.
