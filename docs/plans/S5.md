## What gets built

1. `plugin/scripts/asbuild_setup.py`: standard library only. It runs `git` and `gh` as programs (found with `shutil.which`, so no shell syntax and no Git Bash are needed). It never touches the user's folder: every commit is made with Git's own plumbing on a temporary index, so unsaved work, the current branch and untracked files stay as they are.
2. `plugin/workflows/asbuild-test.yml` and `plugin/workflows/asbuild-verdict.yml`: copies of `workflows/`, held byte for byte equal by a unit test. Setup writes these; nothing is downloaded.
3. `plugin/skills/setup/SKILL.md`: run the script with `python "${CLAUDE_PLUGIN_ROOT}/scripts/asbuild_setup.py"`; pass on its message as it is; never enter a password, key or token; after the person says the pull request is merged, `git fetch origin` and `git switch main` (or `git pull` on `main`), and, if Git refuses over an untracked file, ask before moving the person's copy aside, never delete it (review round 2, N4); then offer `/asbuild:story`. Its description names the unwired case (`.github/workflows/asbuild-test.yml` not on `origin/main`), so Claude reaches setup when someone asks for a story in an unwired repository. The story and verdict skills do not change.
4. The README's `## Install` section, rewritten (below).
5. Release `v0.3.0` (D32: the plugin and the code the workflows fetch share one number): the plugin's version and both workflow files' `--branch` move to `v0.3.0`. After the owner publishes the tag, the judged repositories (asbuild-demo, auto-job-search) are updated by running setup itself: its "older workflow files" case, the evidence for that row.

## What the script does (the checks of this story)

Run from the repository's root: `python asbuild_setup.py [--repo DIR] [--no-open]`. Exit 0: done, or nothing to do. Exit 1: the person must do one thing; the message names it and ends "Then run /asbuild:setup again." Exit 2: setup could not run (Git failed in a way it cannot explain); a missing Git is exit 1, with its install line. Each message is printed as its step is done: on an empty repository `main` is uploaded first, and that is reported even when a later step stops (review round 1, M1).

| ID | It finds | It does | Exit |
| --- | --- | --- | --- |
| S5-C1 | Not a Git repository; no `origin`; `origin` is not on github.com | Says which, and the one next step | 1 |
| S5-C2 | Git has no name or no email | Names the two `git config --global` commands; changes nothing | 1 |
| S5-C3 | The GitHub CLI is missing, or `gh auth status` says not signed in | Names the install line, or `gh auth login` and its choices (GitHub.com, HTTPS, sign in with a browser) | 1 |
| S5-C4 | An empty repository (no branch on GitHub) | When the folder already has commits, stops and names `git push -u origin HEAD:main` (exit 1; review round 1, H1). Otherwise makes the first commit, `requirements.txt` listing pytest (the folder's own `requirements.txt` with `pytest` added if it has one), pushes it as `main`, then carries on as S5-C6 (V3-1A, V3-2A, V3-3A) | carries on |
| S5-C5 | GitHub's default branch is not `main` | Stops with the receipt's own fix: Settings, General, Default branch, `main`; when GitHub has no `main`, rename the default branch to `main` (review round 2, N3) | 1 |
| S5-C6 | The two files are missing on `main` | Pushes branch `asbuild-setup` (one commit on `main`: the two workflow files, and `requirements.txt` with pytest when it lacks it, V3-2A) and opens GitHub's pull request page, `https://github.com/<owner>/<repo>/compare/main...asbuild-setup?quick_pull=1&title=…&body=…`; prints the link; says this pull request gets no verdict | 0 |
| S5-C7 | The two files on `main` equal the plugin's | "AsBuild is already set up here."; pushes nothing | 0 |
| S5-C8 | Older or changed workflow files on `main`, the verdict file among them (review round 2, N5) | The same as S5-C6, and says this pull request changes protected files, so AsBuild's verdict on it is WAITING FOR YOU, as expected | 0 |
| S5-C9 | `asbuild-setup` is already on GitHub (setup ran before) | When it is one commit on today's `main` with the same files: prints the same link again and pushes nothing. Otherwise (different files, or an old branch from an earlier, merged setup) replaces it with one commit on today's `main` (`--force-with-lease`; review round 1, M2), but only when every commit on it that `main` lacks is setup's own ("Add AsBuild" or "Update AsBuild"); otherwise stops and leaves it alone (review round 2, N1) | 0 or 1 |
| S5-C10 | The push is refused for the `workflow` scope | Names `gh auth refresh -h github.com -s workflow`, and `gh auth setup-git` if Git uses another sign-in; nothing else is pushed | 1 |

Git's network calls run with `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so a missing sign-in fails with a message instead of waiting for a prompt nobody sees.

## Premortem: how S5 could fail

1. **The plugin's skills do not show in a local Code session after the desktop app's menus**, so step 1 of the new README is wrong. Test: the owner's check (open a new local Code session, type `/asbuild`, look for `asbuild:story`, note whether `/reload-plugins` was needed), before the README's step 1 is final.
2. **The script behaves differently on Windows** (PowerShell without Git Bash, `gh.exe` against a fake `gh.cmd`, paths with spaces, line endings in the workflow files). Test: the acceptance rows run on `windows-latest` in the clean-install job, in a folder whose path holds a space; the files on the stand-in are compared byte for byte.
3. **Setup changes or loses the person's work** (a switched branch, a staged file, an overwritten `requirements.txt`). Test: every acceptance row checks the folder's `git status`, current branch and files are unchanged after the run.
4. **A message tells the person something untrue or leaves them stuck** (a sign-in that is fine reported as missing, a refusal with no next step). Test: each exit-1 row asserts the exact one next step and "Then run /asbuild:setup again."; a fresh walker repeats the install rows from the README alone after the release.
5. **The release breaks the judged repositories** (`v0.3.0` named before the tag exists). Mitigation: as for `v0.2.1`: the owner publishes the tag on the merge commit, then setup updates each judged repository, and a fresh verdict on each.
