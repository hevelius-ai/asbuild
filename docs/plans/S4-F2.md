# S4 fix plan: a repository whose default branch is not `main` (walkthrough F2 HIGH, F1 MEDIUM)

Decision 18B (D36), 12 Nov 2026. Found by the user walkthrough's run 2 (S3, S4) on a new, empty repository. Estimate 2 to 3 agent hours, then the release `v0.2.1`, the two pin pull requests and a re-check of the failed rows only.

## The defect

- `asbuild-test.yml` runs on pull requests into `main` (`branches: [main]`). `asbuild-verdict.yml` looks for an open pull request into the repository's default branch (`MAIN: default_branch`). On a new, empty repository GitHub makes the first branch pushed the default; following README step 2 that is `asbuild-setup`. The verdict run then finds nothing, ends green ("nothing to judge"), posts no AsBuild check, and the wait script waits its full 20 minutes in silence (F2).
- README step 2 assumes a repository that already has `main`, code and a `requirements.txt`, and a Git identity (F1).

## Criteria

1. When the default branch is not `main` and an open pull request into `main` from this repository has the commit as its head, the verdict job posts one AsBuild check, `AsBuild: UNRESOLVED`, whose summary names the default branch and the fix (make `main` the default branch, then push again), and one receipt whose plain top says the same in plain words and passes the receipt lint. Nothing else runs: AsBuild is not fetched and no verdict is computed.
2. When the default branch is `main`, nothing changes. When no pull request into `main` or into the default branch has the commit as its head, the job still judges nothing and posts nothing.
3. The wait script needs no change: it reads `AsBuild: UNRESOLVED` and exits 3 with the summary.
4. README, "What your repository needs": `main` must be the default branch and already hold a first commit (the code and `requirements.txt`); on a new, empty repository, push `main` first; Git needs a name and an email. The UNRESOLVED line names this cause.

## Tests first, seen failing

In `tests/unit/test_default_branch.py`:

- the lookup step, run in bash with a fake `gh` on `PATH`: default `asbuild-setup` with a pull request into `main` gives `number` and `other_main=asbuild-setup`; default `main` gives `number` and no `other_main`; no pull request gives `skip=true` (needs `jq`, so it runs in CI's Linux check; skipped where `jq` is missing);
- the fetch, Python set-up, download and compute steps do not run when `other_main` is set;
- the check-run step, run in bash with a fake `gh`, posts `AsBuild: UNRESOLVED`, conclusion `failure`, and a summary naming the default branch (needs `jq`);
- the receipt step's plain sentence for this case passes `lint_plain`;
- the README names the default-branch need and the Git identity.

The locked S1 checks stay unchanged and must pass: one step posts check runs, one step's script names `receipt.md`, the trusted job never names `pytest`, its checkout stays on the default branch.

## Premortem

1. **A locked S1 check breaks** (one `receipt.md` step, one check-run step, no `pytest` in the trusted job). Mitigation: the new case reuses the two posting steps' fallbacks; the locked tests run locally before the push.
2. **The plain receipt fails the lint** (it must explain a branch without the word). Mitigation: a unit test lints the exact sentence.
3. **The new path posts a verdict on a pull request it should not judge** (a fork, or a pull request into another branch). Mitigation: the second lookup keeps every clause of the first (same repository, head is the commit, open) and only swaps the base for `main`; tests cover no pull request and the normal path.
4. **The shell tests cannot run on Windows** (`jq`). Stated limit: they run in CI's Linux check, which decides (2.4); locally they skip, and the structural tests run everywhere.
5. **The judged repositories keep the old behaviour** until they pin to `v0.2.1`. Mitigation: the release steps (tag, two pin pull requests), then a fresh verdict, as for `v0.2.0`.

## Release after the merge

The owner merges; the owner publishes `v0.2.1` on the merge commit; two pin pull requests (asbuild-demo, auto-job-search; WAITING FOR YOU, expected); a fresh verdict; then a fresh walker repeats only the failed and blocked rows of run 2 (S3-1, S3-3a), once, with no word about the fixes, in a new, empty test repository.
