## Release steps

Step 1 runs during the review; steps 2 to 6 follow once the pull request is green and reviewed. A difference found
before the publish stops the release; one found after it is graded like a review finding, and a fix ships as `v0.4.1`
(D32: a new tag and plugin version); the release is not called done until then.

1. **Level 2 live run** (design §4.6, "before each release"), in the background during the review:
   `tests/conformance/live.py` on `m4/release` in `hevelius-ai/asbuild-live` (D51), the clone pointed at the branch
   as in M2 (test-only). Expected: every live row as expected (M2: 26 of 26; 24 rows' expectations are in
   `cases.json`, two, `live-js-alias` and `live-mixed-install-fails`, in `live.py`). The results name the commit the
   run judged, and `git diff <it> <the merge commit> -- engine workflows plugin/workflows` must be empty; if a later
   commit changes those, the run is repeated.
2. **The owner merges** the pull request, then **publishes `v0.4.0`** on the merge commit (not a draft or
   pre-release). Between the merge and the publish, repositories set up from `main` fail closed (D49), for minutes.
3. **Check the release:** the tag's commit is the merge commit; a fresh `git clone --depth 1 --branch v0.4.0` has
   `engine` tree `d9e1d741...`, the id in all four workflow files; the `v*` tag ruleset still protects it.
4. **Done line 2, the demo:** setup, run from the `v0.4.0` release's copy of the script, in `hevelius-ai/asbuild-demo`
   (v0.3.1 to v0.4.0): its update pull request gets WAITING FOR YOU (the two protected workflow files, no story), as
   in every earlier release; the owner merges it. Then demo #3 to #6 are closed and reopened one at a time, never
   re-run: a re-run replays the run's first merge commit and its old test job (on 12 Nov the re-run of #3's test run
   still cloned `--branch main`, run 42890559539 attempt 2), while a reopen makes a new merge commit holding `main`'s
   v0.4.0 files. In each new run's log both the test job and the verdict job must clone `v0.4.0`, and the verdict
   must be the one the demo has given at every re-run since v0.2.0 (last on v0.2.1, 12 Nov; v0.3.x never re-ran it):
   #3 PROVEN, #4 NOT PROVEN, #5 WAITING FOR YOU, #6 UNRESOLVED. `hevelius-ai/auto-job-search` stays on v0.3.1, as it
   did through v0.3.4.
   GitHub starts no run for a pull request that conflicts with `main`; all four were mergeable on 18 Nov. If one
   conflicts and its reopen shows no run, step 4 stops there and the owner is told.
5. **Done line 3, the release walkthrough** (skill `user-walkthrough-qa`; D31, D42): a fresh headless walker
   (`claude-sonnet-5-5`, high effort, deny rules on reading the repositories and the installed plugin), in a new
   folder outside the repositories, with the README at `v0.4.0`, the requirements (done line 3 and design §3.1, cut by
   program) and the walker's rules (cut by program). Test target: a new private repository,
   `hevelius-ai/asbuild-walkthrough-6`, whose first commit (D22) is a `create-vite` React + TypeScript app (the
   template's current version, as in P-VITE8) with a shadcn `Button` and the `@` alias, built and checked in Docker
   first. Before the run, AsBuild and the `hevelius-ai` marketplace are removed from this computer, so the walker
   installs from the README; Node.js 24 is already here (a stated limit: the walker cannot show installing it). After
   the run, the D42 check (the target's settings, the installed version). HIGH and MEDIUM findings are handled like
   review findings (2.5).
6. **The owner's own try** comes last (about 1 hour in the plan's owner budget), in a repository of their choice.

## Premortem

1. **The tag's engine is not the pinned one** (an `engine/` change slips in after the pin, or the tag is put on the
   wrong commit), so every repository fails closed. Test: the pin equals `git rev-parse HEAD:engine` (existing test);
   release step 3 checks the published tag itself before anything else uses it.
2. **The version bump changes a Python step** (done line 2). Test: `test_workflow_js` compares every other line with
   v0.3.4's file; release step 4 runs v0.4.0's own test job and verdict on the demo's four pull requests (reopened,
   not re-run), so the released Python steps are judged on real Python pull requests.
3. **Real GitHub has moved since M2** (a runner image, npm, the registry), so a live row changes. Release step 1 runs
   Level 2 again before the publish; a difference stops the release and is investigated (2.9).
4. **The walker cannot finish the JavaScript path from the README alone** (done line 3). The README's install block and
   setup's messages name Node.js (M3); the walker's FAIL or stuck point is graded and fixed before the release is
   called done; the owner's own try comes after.
5. **The release is called done with a known issue unreviewed.** M4-1 is laid out before the publish; the owner's
   answers go in the decision log.
