## 1. Who it is for, measured

- Claude Code pull requests on GitHub by repository language (P11): TypeScript 32.5%, Python 20.4%, JavaScript 9.1%, Rust 7.5%, Go 4.9%, Swift 1.7%, Dart 0.8%.
- Builder-made projects on GitHub (P10, 25 per tool): Lovable 24/25 TypeScript, 76% Vite; Bolt mostly TypeScript; Replit mixed. A real test command in 16 to 36%; Vitest in 4 to 20%, Jest in 0 to 4%, Playwright in 0 to 8%. v0 was not sampled.
- Builder-made lockfiles are often broken for a strict install: 3 of 4 sampled Lovable apps fail `npm ci` (Mac-only packages, a lockfile out of step, a peer clash: JS-8), and Bun's own lockfile rescues only 1 (JS-13). Set up the way the first story will do it, all 4 install strictly, run their own suite, and pass a component check and an `@/` check (JS-15, JS-17, JS-18).
- AsBuild still judges GitHub pull requests built with Claude Code (D14). Builder users meet it after they clone the project and open it in Claude Code.

## 2. Done for v0.4.0 (three lines)

1. In a throwaway private repository holding a small React + Vite + TypeScript app, every row of the JavaScript conformance column (§4.6) gets its expected verdict from the real workflows; no cheat row is ever PROVEN.
2. Python-only repositories get exactly v0.3.4's results: the locked S1 to S5 tests and the unit suite pass unchanged, the Python column matches v0.3.4's golden files, and the demo's four pull requests give the same verdicts. Python repositories that also hold JavaScript files get only the differences listed in §3.2, each a conformance row.
3. A fresh agent following only the README, in a new repository holding a copy of a Vite + React + TypeScript app built from the official `create-vite` template with a shadcn `Button` (Vite is used by 19 of 25 sampled Lovable apps; React with shadcn by all four proof apps), reaches a PROVEN build with the same commands and merges as the Python path (setup: one command, one merge; story: one pull request, one merge; build: one pull request, PROVEN), plus installing Node.js.

### 3.2 A Python project that also holds JavaScript files (the differences, stated)

- Protected names (L5 B): nothing changes until the repository has agreed JavaScript checks; from then on a build that changes any of the thirteen new names (full list in §4.4) waits for the person.
- Setup: a repository with a root `package.json`, no `requirements.txt`, no `pyproject.toml` and no `.py` file tracked on main (read from main's tree, as setup already reads files, so packages installed under `node_modules` never count) is treated as JavaScript; a repository with no root `package.json`, one below the root and none of those Python markers stops with "not yet". Any repository holding a `.py` file, `requirements.txt` or `pyproject.toml` goes the Python way, as today, with no new question. The one change: a repository with no Python file at all and a root `package.json`, where today setup would add `requirements.txt` with pytest, is now set up as JavaScript or stopped. Each case is a conformance row (§4.6).
- Test job: the JavaScript steps run only when the repository holds agreed JavaScript checks (`hashFiles('tests/acceptance/**/*.test.*')`), so a Python repository with a front end and only Python checks runs exactly today's steps.

## 4. The design

### 4.1 The seam (Fable)

The trusted half keeps reading data only. Language-bound pieces move behind one table, `engine/langs.py`, keyed by the file extension of the locked acceptance files: which result files to read; how a test name carries a check ID; how a locked test is found in the results (Python: file stem against the dotted class name, as today; JavaScript: file path and title); how the lock lists tests; how the story is read from a result; which failure rules apply. Python's row is today's code, moved unchanged. A language is in play only when main's `locks.json` holds a file it owns.

### 4.2 Test job (untrusted, `pull_request` only, read-only token)

One `asbuild-test.yml`. Python steps keep their text and their gate. JavaScript steps run `if: hashFiles('tests/acceptance/**/*.test.*') != ''` (to prove: P-CI-1), each with `continue-on-error: true` and its own `timeout-minutes`, placed after the Python steps and before the shared fails-before step, so a JavaScript failure cannot skip the Python evidence:

1. `actions/setup-node`, pinned by commit, Node 24, no cache.
2. `npm ci --no-audit --no-fund --legacy-peer-deps` (L3 option A): the lockfile fixes every version; peer versions are not enforced, as Bun does. On failure the step writes npm's error code only (`EBADPLATFORM`, `ERESOLVE`, `EUSAGE` or `OTHER`, matched by a fixed pattern) to `out/js-install.txt`.
3. Full suite: `node_modules/.bin/vitest run --reporter=junit --outputFile=out/pr-js.xml` (the project's own settings: these are the app's other checks).
4. Agreed checks, hardened: `node_modules/.bin/vitest run --config "$ASBUILD/engine/js/vitest.acceptance.mjs" --root . --reporter=junit --outputFile=out/acceptance-js.xml`.
5. Fails before: `c3_overlay.py` picks the runner by extension; each JavaScript check file is laid over main in a worktree at `.asbuild-c3/<slug>/` inside the checkout and run with AsBuild's settings, using the pull request's `node_modules` (JS-7).

Tools start from `node_modules/.bin`, never through `npm run` or `npx`, so `package.json` scripts and `.npmrc` play no part in the runs.

### 4.3 The hardened run (L2)

AsBuild's settings file (`engine/js/vitest.acceptance.mjs`, inside the tree-checked engine folder) imports only Node's built-ins, so it loads from outside the project on any Vite. It reads the project's tsconfig `paths` itself (`tsconfig.json`, then `tsconfig.app.json`, following relative `extends`) and turns them into aliases, dropping any alias for the test tools (`vitest`, `@vitest`, `vite`, `@testing-library`) or pointing outside the project; it never reads the project's Vite or Vitest config. It sets the automatic JSX runtime (`esbuild.jsx` for Vite up to 7, `oxc.jsx` for Vite 8), `setupFiles: []`, `globalSetup: []`, `retry: 0`, `passWithNoTests: false`, `include: ["tests/acceptance/**/*.test.?(c|m)[jt]s?(x)"]`. (Vite's own `resolve.tsconfigPaths` works only on Vite 8: JS-16.) Proven:

- A project's own settings with a cheating setup file make a wrong app pass a locked check, including through a freely named setup file no protected name covers (JS-3, JS-6; on Vitest 5.1 and 4.1: JS-9). AsBuild's settings stop it on all six Vitest/Vite pairs tested, Vite 5 to 8: the wrong app fails by assertion (JS-17, JS-18).
- A tsconfig `paths` entry pointing `vitest` at a stub, in an extended unprotected file, does not fool AsBuild's settings: the settings drop the alias and the wrong app fails by assertion on all four table pairs (JS-20; one form of the trick tested).
- On four real Lovable apps, set up as the first story will do it, a check rendering the app's own `Button` and a check importing `@/lib/utils` both pass with no setup file (JS-18); a Radix `Accordion` renders (JS-11). A whole page renders only inside a router (`MemoryRouter` at its address; JS-11).

Stated limits: (1) as D16 line 3, the job runs the pull request's code; install scripts or app code can still change the test tool on disk; (2) a component that needs a browser feature jsdom lacks can be checked only if the check itself provides it (no shared setup files); (3) one form of the tsconfig trick was tested; `extends` given as an array or a package name is not followed, so its paths are not read (a check that needs them fails to load and the verdict waits for the person). The product's tsconfig reader is a proper parser with its own tests; the proof's reader could mistake a `**/` glob for a comment (round-3 note).

### 4.4 Engine (trusted)

- Failure rules are chosen by the language row, never by whether `type` is filled. JavaScript: `AssertionError` is strong; existence-only for `ReferenceError`, a `TypeError` saying "is not a function" or "is not a constructor", messages "Cannot find module", "Cannot find package", "Failed to resolve import", "does not provide an export named", "Element type is invalid" (JS-14), and a file that could not load (one testcase named after the file: JS-1, JS-9); a JavaScript failure with an empty `type` is unreadable and gives UNRESOLVED; every other failure is strong. Python's rules are unchanged.
- The result shapes are proven on Vitest 3.2.4, 4.1.12 and 5.1.0 with Vite 5 to 8 (JS-9, JS-17). Vitest must run on the app's own Vite, or the app's own plugins fail to load (JS-16: `does not provide an export named 'isFileLoadingAllowed'`), so the story skill picks Vitest from a fixed table keyed by the app's Vite major (Vite 5 and 6: Vitest 3.2.x; Vite 7: 4.1.x; Vite 8: 5.1.x; each pair proven in JS-17) and never by "newest that installs" (`--legacy-peer-deps` turns npm's peer check off). The story-time check refuses a Vite or Vitest outside the table, in plain words.
- A file that could not load lists none of its tests, so its checks are taken from main's lock and the story, and all count existence-only.
- Earlier stories' checks (round 3, HIGH): in a repository with JavaScript checks, a locked acceptance test of another story that fails in AsBuild's hardened run (`acceptance-js.xml`) counts as "something that worked before broke" (`PASS_TO_PASS_BROKEN`), whatever the app's own full run says, unless it belongs to a story not built yet and fails on main too (today's rule). The app's own run, which uses the project's settings, can no longer hide it. Conformance row "earlier story masked by a setup file".
- `matches` splits names on any non-letter, non-digit character; for Python names (letters, digits, `_`) the result is identical (P-ENG-1 checks every existing name). `story_of` reads `tests/acceptance/S<n>/` from the path.
- `lock_check.entry(raw, path="")`: byte-identical for `.py`; for JavaScript test files, the literal titles of top-level `test(`/`it(` calls.
- Protected names add `package.json`, `npm-shrinkwrap.json`, `.npmrc`, `bun.lockb`, `.yarnrc*`, `pnpm-workspace.yaml`, `vite.config.*`, `vitest.config.*`, `vitest.workspace.*`, `tsconfig*.json`, `jsconfig.json`, `.nvmrc`, `.node-version`. Scope (L5 B): they apply only when main's or the pull request's `locks.json` lists a JavaScript check file; a pull request can change neither main's file nor, outside a story pull request, its own story entries. Conformance rows: a Python repository with a front end, before and after its first JavaScript story. `receipt.py` maps them to its existing plain phrases.
- A story pull request whose new locked checks are JavaScript files and whose only protected changes are `package.json` and `package-lock.json` gets a new code, `STORY_ADDS_TOOLS` (a Python story keeps today's wording), worded from what the engine knows: "It also changes the list of software your app installs; approving the checks approves that change too." (must pass `lint_plain`).
- An install failure gives UNRESOLVED as today; when `out/js-install.txt` holds one of the three known codes, the receipt adds one fixed sentence for it (for example `EBADPLATFORM`: "Your app's list of software includes parts that only work on another kind of computer, so GitHub could not install it."). The code comes from the untrusted job, so at worst a forged code shows the wrong fixed sentence under a verdict that claims nothing.

### 4.5 Story time, setup, skills, README

- Story-time checks choose the language by extension. For JavaScript: a standard-library scanner finds top-level `test("S<n>-C<m> ...")` calls with a literal title, one check per file; refuses `describe`, `.only`, `.skip`, `.todo`, `.each`, `${` in titles. It runs the story's files on main (worktree, AsBuild settings) and needs each to fail by assertion; it checks each approved example appears as a literal inside an `expect(...)` chain. How Vitest starts from Python in a worktree on Windows is to prove (P-WIN-1: the runner's npm failed, JS-10).
- The first story pull request, for a JavaScript project: always repairs the lockfile once, by content and not by a local failure (a Mac-only package installs on a Mac): it removes `node_modules` (as JS-21 and JS-22 did; the tool install right after rebuilds it), drops names made for one platform (`*-darwin-*`, `*-win32-*`, `*-linux-*` and the like) from `dependencies` and `devDependencies` only (never `optionalDependencies`, where such names are a known workaround), then rewrites the lockfile with `npm install --package-lock-only --legacy-peer-deps` (JS-15 on Linux; on the person's computer with npm 11: Mac 4 of 4, JS-19; Windows 4 of 4, JS-22; with npm 10 on Windows 1 of 4 lost the Linux packages, JS-19 and JS-21, so npm 11.19 or newer is required); then it installs the test tools with one named command: `npm install --save-dev --save-exact --legacy-peer-deps vitest@<from the table> jsdom @testing-library/react @testing-library/dom` (JS-17: 4 of 4 apps). The skill's `javascript.md` says: one file per check, `// @vitest-environment jsdom`, a page inside `MemoryRouter`, render what the person sees and assert the approved words literally, never add a setup file.
- Setup: JavaScript when the root has `package.json` and the repository holds no `requirements.txt`, `pyproject.toml` or `.py` file; it adds nothing, checks for Node 24 or newer with npm 11.19 or newer, and stops in plain words for every shape in §3.1's last row (one list, used by setup and by premortem 5). The subfolder stop is checked first, with the same Python markers.
- README: one needs line for JavaScript/TypeScript (React with Vite), the install line for Node, and an unnumbered line under "What AsBuild does not prove" (S4-C2 keeps D16's four numbered items): only Vitest tests count as the app's other checks.

### 4.6 Proof system (permanent)

`tests/conformance/`: the same rows for every language (proven, check-fails, story, no-results, existence-only, weakened-check, tampered-settings), plus JavaScript rows (setup-file cheat, tsconfig-paths cheat, earlier story masked by a setup file, `.npmrc`, `package.json` script, platform-only package, lockfile out of step, component not written yet, story that repairs the lockfile, and, per table pair (Vite 5, 6, 7 and 8), a proven-build row and an existence-only row), Python rows for a repository that also holds `package.json` (with and without JavaScript checks), and setup rows (Python files with a `package.json` in a subfolder; both files at the root; no Python file and a root tooling `package.json`). Level 1 runs in AsBuild's CI on every pull request; Level 2 (`live.py`) pushes the same trees to a throwaway private repository before each release and reads the posted verdicts. Python golden files from v0.3.4 must match byte for byte.

## 7. Premortem

1. JavaScript builds add packages often, so builds wait with no line judged (D41). Measure: count over the first 10 real builds; reopening D41 is the owner's call with that number.
2. A builder-made lockfile does not install on GitHub. The first story repairs it once by content, on Mac (npm 11.19.1, `node_modules` present: JS-19) or Windows (npm 11.19.1, `node_modules` removed first: JS-22), 4 of 4 then installing on Linux; a later break gives UNRESOLVED with a fixed sentence naming the kind of cause (§4.4); conformance rows "platform-only package" and "lockfile out of step". Stated limit: a platform-only package added by a later build is caught only on GitHub (UNRESOLVED), and its fix is a pull request the person merges.
3. A new Vitest or Vite major changes the result file or breaks the settings. The story skill installs only table pairs; the story-time check refuses others; an empty `type` gives UNRESOLVED; conformance rows run every table pair. Stated limits: Vite 5 to 8, Vitest 3.2 to 5.1; real apps were proven on Vite 5 only (the four Lovable apps), Vite 6 to 8 on a small test project; a current create-vite app (Vite 8) end to end is in the first milestone (§5); a Vite 4 app stops in plain words.
4. The refactor moves a Python verdict. Golden files, locked tests, the Python column and the demo re-run; any difference stops the release.
5. Scope creep. Setup stops for exactly the shapes in §3.1; each new request is one parking line; adding one needs a design gate and a conformance column.
